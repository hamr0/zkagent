## Key decisions

- **D13 — disclosure splits into two modes**, resolving the FR6 deadlock the prior stash left open. Checked the EU Age Verification Blueprint (`ageverification.dev`, `eu-digital-identity-wallet/av-doc-technical-specification`) against the question "does age verification require linkability" — answer: no, the EU design actively engineers AGAINST it. Quoted: §4.2 "SHALL use a Proof of Age attestation only once and then remove it from the batch," §4.3 "SHALL support batch issuance," §4.3 "SHALL set the timestamp… with a precision that limits the linkability information," §2.4 "Domain-specific identifiers, or pseudonyms, are used to enable users to avoid relying on the same unique identifier." Their batch-of-30 machinery exists only because their wallet must round-trip to an issuer and cannot do ZK; zkagent has no issuer in the read path (re-derives from the chip locally), so per-presentation freshness is free — no batching needed. Result: **Mode A** (anonymous, default) — one bit + attestation + nonce, no identifier, unlinkable across presentations. **Mode B** (pseudonymous, opt-in, requested explicitly in the challenge) — adds the domain-scoped `zktag`. Mode B is the only mode that can carry uniqueness/blocking; mode A can never emit a stable identifier (new **NO-GO #11**). Extended with a one-liner: the agent layer is mode-B-only structurally (a delegation cert needs a persistent human root to bind to; mode A emits nothing to bind to).
- **D14 — `acceptedDocuments` defaults greedy** (accept every ICAO 9303 document), falling out of D13 for free: `k` (the uniqueness cost of holding multiple documents) only exists in mode B; mode A has zero cost to reach, so there's no reason to narrow it by default.
- **D15 — FR6 (uniformity) narrowed, not retired.** Uniformity required within one client build+mode; cross-client distinguishability is now accepted and is the mechanism the trust list runs on. Safe only because of D16/FR11 and D17/FR10 below.
- **D16 / FR11 — the derivation must be a published, versioned spec** (`zkagent-derivation/1`), so two different client apps compute the identical zktag for the same document+domain. This is what makes cross-client distinguishability safe: a visible client identity partitions the *anonymity set*, not the *identity space*.
- **D17 / FR10 — the trust list (accepted client package+cert-digest pairs) is held by the OPERATOR, never by us.** No registry, per NO-GO #3.
- **New FR9 + milestone M1b + Q15** — mode A's "no identifier" claim covers the WHOLE payload including the attestation itself, not just zkagent's own fields: a reused attestation key, a device-unique cert intermediate, an OS/patch-level string, or a precise timestamp would each silently reintroduce linkability. Gated behind a black-box byte probe with a DELIBERATELY PLANTED positive control (borrowed from 8een §7.3 method — see prior stash), which must prove the test can fail. Until M1b runs, mode A is documented as "design intent," not a demonstrated property. This blocks M3.
- **New Q18 — chip cloning, discovered while writing the design companion doc, load-bearing for mode B.** Verifying the SOD is PASSIVE authentication only — it proves the government signed the bytes, not that the chip presenting them is the original. The BAC/PACE unlock key is the MRZ, which lives INSIDE the DG1 dump itself, so anyone holding a one-time-captured dump (kiosk, hotel, KYC flow, a leaked scan) holds both lock and key and can replay it from an emulator (Android HCE, Proxmark). The replay produces a BYTE-IDENTICAL zktag to the real document. This doesn't just add a threat — it **dismantles D10's stated rationale**: D10 assumed a 30-day secret-expiry ceiling makes renewed possession costly because it requires physically re-scanning the real document; a clone defeats that entirely, since the holder of the dump can re-scan their emulator indefinitely. Defence is Active Authentication (AA) or Chip Authentication (CA) — the chip proving it holds a private key that never leaves it — but AA is OPTIONAL in ICAO 9303 and some countries omit it deliberately on privacy grounds (an AA signature can itself be used to prove presence at a place/time). M0's chip-field-inventory checkpoint extended to also report AA/CA support. Mode A is UNAFFECTED — nothing to impersonate; a cloned chip proves an age that was genuinely true of the original holder.
- **D18 — sequencing freeze.** The rung-2 agent layer (delegation certs, RFC 9421 signing, M4–M5) is not to be designed, discussed, or specified further until the age-verification leg (rung 1, M0–M3) ships. Rationale recorded in the PRD from this session's own evidence: Q18 sat undetected through four PRD revisions and only surfaced when the read path had to be written out concretely for the design companion doc — more design was producing more surface, not more certainty. Refused by default even on a "just discuss it" ask in passing.
- **D2 amended — development device settled: Pixel, stock ROM, all other vendors excluded for M0–M2.** NFC Type A/B support is NOT the discriminator (baseline on essentially every phone-class NFC controller); the extended-length-APDU variance that drives commercial ID-verification vendors' device blocklists doesn't apply to zkagent because it never reads DG2 (the facial image, 15–30KB) — only DG1 (~100 bytes) + SOD (~1–2KB), which fit in short APDUs with chaining on any chipset. The real discriminator is attestation quality (Q14b) — Pixel gives the reference Google implementation, guaranteed StrongBox (Titan M2), stock ROM, longest debuggability. Huawei and China-market ROMs excluded outright (no Play Services, non-Google attestation root). Framed explicitly as a debuggability choice, not a capability one: on a Pixel a failure means the code is wrong; on an unpredictable OEM it might be the vendor's Keymaster instead.
- **D12 — package name split finalized: project stays `zkagent`, published package is `chiproof`.** Precedent: owner's own `8een` project / `zk8een` package pattern. Checked npm availability 2026-08-07 (`chiproof` → 404, free; `chipproof`/`docchip`/`barechip` also free) — owner's pick was `chiproof` ("one p").
- **Q17 (legal sufficiency) reframed per owner instruction**: NOT contesting the regulatory requirement, NOT seeking certification — the point is demonstrating the same privacy properties are achievable with far less machinery than the official route requires. Lowers the bar (a demonstration must be honest, not certified) without removing the question — still gates any shift from demonstration to pitch.

Owner asked about 4 Vinted listings (2× Pixel 6a, 1× Pixel 7 128GB, 1× more Pixel 6a). Rendered via `mcp__barebrowse__browse` (plain WebFetch got served an unrendered "Removed!" shell — Vinted needs JS execution) and extracted structured attributes (price, condition, seller rating, SIM lock status), since the free-text descriptions weren't rendered by the fetcher.

Reasoning: SIM lock is irrelevant to every M0–M5 requirement (NFC read, SOD verification, zktag derivation are all offline/USB-only — no cellular touchpoint anywhere in the design per NO-GO #1), so paying more to avoid a SIM lock buys a capability the product design deliberately never uses. Flagged one thing to verify before paying: confirm stock ROM / locked bootloader with the seller, since an unlocked bootloader (not the SIM lock) is the actual disqualifier for attestation later.

Follow-up: owner asked whether "two lines on screen" (an unspecified listing, never confirmed which one) indicates progressive failure. Answered: yes, treat as progressive by default — OLED line defects are typically a failing chip-on-film/flex bond at the display driver, which degrades further under thermal cycling and pressure; two diagnostics offered (does it change with pressure/temperature; did it appear after a drop or spontaneously), but owner never confirmed which listing had the defect. Key mitigating insight: M0's own gotcha list only needs the screen to reach ADB during initial setup (enable developer options + USB debugging), after which `scrcpy` mirrors the framebuffer over USB regardless of physical display state — a screen defect is fatal only in the first ~30 minutes of ownership, not for the rest of M0–M2 testing. Recommended NOT carrying a degrading panel into M2 (weeks of iteration) even though it's fine for M0.

Owner asked "is Google Nexus 6 class A/B" (apparently already owns one). Answered: yes, has NFC-A/B, but disqualified as the M2+ dev device — no StrongBox (arrived Pixel 3+), no fingerprint sensor at all (breaks FR1's biometric-gate testing), security patches ended Oct 2017, fails Play Integrity. Flagged it COULD be a free, throwaway M0-only device, since M0 (chip read, SOD verify, zktag derive-twice) touches no attestation/StrongBox/biometric code at all — recommended factory-reset + airplane-mode + `adb push` the masterlist rather than downloading, given passport data would transit 9-year-unpatched hardware.
